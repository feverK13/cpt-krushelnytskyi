## 2. Мета роботи

Мета роботи – розширити класову модель із лабораторної роботи № 2: винести спільні поля й перевірки товару до базового типу, виразити відмінності категорій окремими підтипами з різною реалізацією спільного методу, додати `enum` для категорії, реалізувати рівність об’єктів і обробляти різнорідні товари через спільний тип без розгалужень за підтипом. Вхідний формат, показники й звіт при цьому не змінюються.

Досягнутий стан продукту:

- `Product` – абстрактний запечатаний (`sealed`) клас із трьома `final`-підтипами `Laptop`, `Peripheral` і `OtherProduct`; усі поля, перевірки й повідомлення про помилки лабораторної роботи № 2 лишилися в базовому класі, підтипи не містять перевірок і дубльованих полів;

- поліморфна операція `warrantyCost()`: різні правила в кожному підтипі, без `if` і `switch` за підтипом; список `List<Product>` обробляється як раніше, класи `InputProcessor` і `MetricsCalculator` не змінено;
- узгоджені `equals` і `hashCode` (той самий клас і всі п’ять полів), перевірені в `HashSet` і `HashMap`;
- необов’язковий прапорець `--warranty-cost` додає до звіту розділ «Гарантійна вартість:»; без нього звіт збігається з еталоном побайтово;
- завдання із зірочкою: `sealed`-ієрархія й `switch` зі зіставленням зі зразком без гілки `default` у `ProductDescriber`, вичерпність перевіряє компілятор;

## 3. Стан до і після цієї роботи

Після лабораторної роботи № 2 проєкт мав один незмінний клас `Product`, який однаково описував будь-який товар. Усі різновиди техніки мали один і той самий набір правил, а єдина операція над товаром – читання полів. Тепер товар має тип, що відповідає його категорії, а відмінність між типами виражена не умовами, а методом, який кожен підтип реалізує по-своєму.

Таблиця 1 – Що саме змінено

| Було (лабораторна робота № 2) | Стало (лабораторна робота № 3) |
|---|---|
| `public final class Product`, публічний конструктор | `public abstract sealed class Product permits Laptop, Peripheral, OtherProduct`, захищений конструктор, фабрики `of`, `fromCsv`, `builder()` |
| один тип для всіх товарів | `Laptop`, `Peripheral`, `OtherProduct` – підтип залежить від категорії |
| категорія – лише рядок | `enum ProductKind`: підпис, множина категорій CSV, створення підтипу, `fromCategory` без винятків |
| у товару немає власної поведінки, крім читання полів | поліморфний метод `warrantyCost()`, різна реалізація в кожному підтипі |
| рівність за посиланням (успадкований `Object.equals`) | `equals` і `hashCode` за класом і п’ятьма полями |
| звіт містить лише чотири показники | додатковий розділ «Гарантійна вартість:» лише з прапорцем `--warranty-cost`; без нього звіт той самий |
| `ValidationError`: 8 причин помилок | додано `CATEGORY_MISMATCH` для узгодженості категорії та типу (недосяжна з CSV) |

Фрагмент класу до і після:

```text
// лабораторна робота № 2
public final class Product {
    public Product(String name, String category, double price, int warrantyMonths, int stock) { ... }
}

// лабораторна робота № 3
public abstract sealed class Product permits Laptop, Peripheral, OtherProduct {
    protected Product(ProductKind kind, String name, String category,
                      double price, int warrantyMonths, int stock) { ... }
    public static Product of(String name, String category, double price, int warrantyMonths, int stock) {
        return ProductKind.fromCategory(category).create(name, category, price, warrantyMonths, stock);
    }
    public abstract double warrantyCost();
}
```

Файли конвеєра `InputProcessor`, `MetricsCalculator`, `CsvReader` і `Metrics` не змінювались: вони працюють зі `List<Product>`, а підтип їм не потрібен. Саме це вимагала методичка: нові підтипи не повинні вимагати переписування коду звітності. Незмінними залишилися CLI (крім нового прапорця), читання файла (UTF-8, BOM, CRLF), журнал, формат звіту, коди завершення 0, 1 і 2, Maven, CI та правила роботи через Issues і Pull Request.

## 4. Базовий тип

Базовий тип – абстрактний клас `Product`. Він містить п’ять спільних полів (`name`, `category`, `price`, `warrantyMonths`, `stock`) і поле `kind` з видом товару; усі шість – `private final`, сеттерів немає, тому об’єкт незмінний. Усі перевірки лабораторної роботи № 2 лишилися тут, у конструкторі, в тому самому порядку й з тими самими повідомленнями: назва, категорія, ціна `> 0`, гарантія `>= 0`, запас `>= 0`.

### 4.1. Інваріанти і порядок перевірок

Таблиця 3 – Перевірки в конструкторі базового класу

| Крок | Поле | Правило | Помилка |
|---|---|---|---|
| 1 | name | не `null`, після `strip()` не порожня | `NullPointerException` / `EMPTY_FIELD` |
| 2 | category | не `null`, після `strip()` не порожня | `NullPointerException` / `EMPTY_FIELD` |
| 3 | price | число, скінченне, `> 0` | `NOT_A_NUMBER`, `TOO_LARGE`, `NEGATIVE`, `NOT_POSITIVE` |
| 4 | warrantyMonths | `>= 0` | `NEGATIVE` |
| 5 | stock | `>= 0` | `NEGATIVE` |
| 6 (нове) | category і kind | категорія належить виду підтипу | `CATEGORY_MISMATCH` |

Шоста перевірка нова: вона виконується після п’яти старих, тому не змінює жодного повідомлення лабораторної роботи № 2. Через фабрики вона недосяжна (вид завжди визначається з категорії), а перевіряє пряме створення підтипу, наприклад `new Laptop("a", "Монітори", ...)`. Це охороняє узгодженість `kind` і категорії, яку не можна порушити навіть у коді того самого пакета.

### 4.2. Абстрактний метод

```text
/** Returns the cost of the warranty in UAH, rounded to two decimals. */
public abstract double warrantyCost();
```

Метод оголошено в базовому класі, а реалізує кожен підтип. Метод читає ціну й гарантію через загальні геттери, тому підтипам не потрібні власні поля.

### 4.3. Чому абстрактний клас, а не інтерфейс

Таблиця 4 – Вибір між абстрактним класом та інтерфейсом

| Критерій | Абстрактний клас `Product` | Інтерфейс |
|---|---|---|
| спільний стан (п’ять полів, `kind`) | зберігається в самому класі | не може мати змінних екземпляра; поля довелося б дублювати в підтипах |
| спільні перевірки | виконуються один раз у конструкторі | конструктора немає; перевірки довелося б виносити в статичний метод і викликати з кожного підтипу |
| `equals` і `hashCode` | реалізуються один раз у базовому класі і закриваються `final` | інтерфейс не може перевизначити методи `Object` |
| декілька базових типів у підтипа | не потрібно: кожен товар – лише товар | потрібно було б, якби підтипи мали різні ролі |

Тому інтерфейс тут не потрібен. Він був би доречним, якби різні за природою типи мали спільну здатність (наприклад, `Comparable`), а в цій роботі підтипи – різновиди одного й того самого товару зі спільним станом, і єдине, що їх відрізняє, – правило розрахунку.

### 4.4. Спадкування чи композиція

Відношення «Laptop – це різновид Product» є справжнім: ноутбук має всі властивості товару й підставляється всюди, де очікується `Product`. Відмінність поведінки при цьому одна – розрахунок гарантійної вартості, і вона визначається категорією, яка не змінюється протягом життя об’єкта. Тому спадкування тут природне. Композиція (`Product` містить об’єкт `WarrantyPolicy` і делегує йому) також спрацювала б і дозволила б змінювати правило під час роботи, але ця можливість не потрібна: політика прив’язана до категорії й не змінюється, а додатковий рівень делегування ускладнив би код без користі. Якби вимога змінилась (наприклад, правила гарантії залежали б від акції, що вмикається окремо), вибір слід було б переглянути на користь композиції.

### 4.5. Створення об’єктів і sealed

Публічного конструктора в `Product` більше немає. Підтип вибирає `ProductKind.fromCategory`, а три фабрики (`of`, `fromCsv`, `builder().build()`) створюють об’єкт саме через нього, тому дістати `Laptop` для категорії «Монітори» неможливо. Конструктори підтипів – package-private, а в самого класу `Product` клаузу `permits` обмежує підтипи трьома. Вид `kind` передається в конструктор базового класу як параметр, а не виводиться перевизначуваним методом: виклик перевизначуваного методу з конструктора міг би виконатися до ініціалізації підтипу.

Клас перестав бути `final`, а його конструктор може кинути виняток, тому SpotBugs (правило `CT_CONSTRUCTOR_THROW`) вимагає закрити атаку через фіналізатор. Це зроблено порожнім `protected final void finalize()` з приміткою; альтернативою було вимкнути правило, що послабило б перевірку для всього проєкту.

## 5. Підтипи

Підтипів три. Два з них – `Laptop` і `Peripheral` – вимагає варіант 10. Третій, `OtherProduct`, запасний: у файлі CSV немає колонки типу, а в лабораторній роботі № 1 коректним був запис із будь-якою непорожньою категорією («Смартфони», «Телевізори», «Побутова техніка»). Без третього підтипу такі рядки стали б хибними, змінився б звіт, а це заборонено. Усі підтипи – `final`, не мають власних полів і не містять перевірок: відмінність виражено лише реалізацією `warrantyCost()`.

Таблиця 5 – Правила гарантійної вартості

| Підтип | Категорії CSV (приклади) | Формула | Константи |
|---|---|---|---|
| `Laptop` | Ноутбуки, Laptops, Notebook | 3 % ціни за кожен рік гарантії + 100 грн за кожен розпочатий рік | `RATE_PER_YEAR = 0.03`, `SURCHARGE_PER_STARTED_YEAR = 100` |
| `Peripheral` | Аксесуари, Монітори, Навушники, Аудіо | 1 % ціни за кожен рік гарантії | `RATE_PER_YEAR = 0.01` |
| `OtherProduct` | усе інше: Смартфони, Телевізори, Побутова техніка | 2 % ціни за кожен рік гарантії | `RATE_PER_YEAR = 0.02` |

Рік гарантії – це `warrantyMonths / 12.0`, результат округлюється до двох знаків; для гарантії 0 місяців вартість 0. Ноутбук дорожчий в обслуговуванні, тому має додатковий фіксований збір за кожен розпочатий рік; для периферії ставка найнижча, бо вона найпростіша у ремонті.

Фрагмент підтипа `Laptop`:

```text
public final class Laptop extends Product {

    public static final double RATE_PER_YEAR = 0.03;
    public static final double SURCHARGE_PER_STARTED_YEAR = 100.0;

    Laptop(String name, String category, double price, int warrantyMonths, int stock) {
        super(ProductKind.LAPTOP, name, category, price, warrantyMonths, stock);
    }

    @Override
    public double warrantyCost() {
        double years = getWarrantyMonths() / 12.0;
        return roundMoney(getPrice() * RATE_PER_YEAR * years
                + SURCHARGE_PER_STARTED_YEAR * Math.ceil(years));
    }
}
```

Виклик `super(...)` у конструкторі підтипу передає базовому класу вид і п’ять полів, і саме там відбувається вся перевірка; підтип нічого не перевіряє. Анотація `@Override` змушує компілятор перевірити, що метод справді перевизначає `warrantyCost()` базового класу: помилка в імені чи сигнатурі стала б помилкою компіляції. Спільне округлення `roundMoney` оголошено один раз у базовому класі.

Таблиця 6 – Приклади розрахунку

| Вхід | Обчислення | Результат |
|---|---|---|
| `Laptop`, 40 000 грн, 24 міс. | 40 000 · 0,03 · 2 + 100 · 2 | 2600.00 грн |
| `Laptop`, 10 000 грн, 18 міс. | 10 000 · 0,03 · 1,5 + 100 · 2 (два розпочаті роки) | 650.00 грн |
| `Peripheral`, 1 500 грн, 12 міс. | 1 500 · 0,01 · 1 | 15.00 грн |

| будь-який підтип, 0 міс. | усі доданки дорівнюють 0 | 0.00 грн |

## 6. enum ProductKind

`ProductKind` – перелік із фіксованою множиною видів товару: `LAPTOP`, `PERIPHERAL`, `OTHER`. Кожна константа має підпис для звіту (`label`), множину назв категорій у CSV і посилання на конструктор свого підтипу (`Laptop::new` тощо). Така побудова зберігає всю відповідність «категорія – вид – підтип» в одному місці.

Таблиця 7 – Константи ProductKind

| Константа | Підпис | Категорії (після `strip()` і нижнього регістру) | Створює |
|---|---|---|---|
| `LAPTOP` | Ноутбук | ноутбуки, ноутбук, laptops, laptop, notebooks, notebook | `Laptop` |
| `PERIPHERAL` | Периферія | аксесуари, периферія, монітори, монітор, клавіатури, миші, мишки, навушники, принтери, аудіо та англійські відповідники | `Peripheral` |
| `OTHER` | Інше | будь-яка інша, у тому числі `null` і порожній текст | `OtherProduct` |

```text
public static ProductKind fromCategory(String category) {
    if (category == null) {
        return OTHER;
    }
    String key = category.strip().toLowerCase(Locale.ROOT);
    for (ProductKind kind : values()) {
        if (kind.categories.contains(key)) {
            return kind;
        }
    }
    return OTHER;
}
```

`fromCategory` ніколи не кидає виняток: невідома категорія – це не помилка, а вид `OTHER`. Помилкою залишається лише порожня категорія, але її відхиляє конструктор `Product` зі старим повідомленням, тому порядок і тексти помилок лабораторної роботи № 2 не змінились. Метод `accepts(String)` повертає `true`, якщо категорія належить цьому виду; конструктор базового класу використовує його для перевірки узгодженості.

Де використано `enum`:

- у моделі: поле `Product.kind`, метод `kind()`; фабрика `Product.of` вибирає підтип через `ProductKind.fromCategory(category).create(...)`;
- у звіті: `label()` дає назву групи в розділі «Гарантійна вартість:» (рядки «Ноутбук, шт.: 1», «Периферія, шт.: 3», «Інше, шт.: 4»);
- у групуванні: `WarrantyCostSummary` збирає товари в `EnumMap<ProductKind, List<Product>>` і виводить групи в порядку оголошення констант.

Значення `enum` порівнюються через `==`: кожна константа існує в одному екземплярі, тож `==` перевіряє тотожність і дає ті самі результати, що й `equals`, але не кидає `NullPointerException` для `null` ліворуч і виявляє порівняння з іншим типом ще під час компіляції. У коді класів вид завжди порівнюється так (`fromCategory(category) == this`).

## 7. equals і hashCode

### 7.1. Критерій рівності

Два товари рівні тоді й лише тоді, коли вони мають **той самий клас** і всі п’ять полів однакові: назва, категорія, ціна (порівняння через `Double.compare`), гарантія й запас. Критерій вибрано за змістом: два записи з однаковими даними описують один і той самий товар. Усі поля незмінні, отже результат `equals` і `hashCode` не змінюється протягом життя об’єкта, і товар можна безпечно використовувати як ключ `HashMap`.

```text
@Override
public final boolean equals(Object o) {
    if (this == o) {
        return true;
    }
    if (o == null || getClass() != o.getClass()) {
        return false;
    }
    Product other = (Product) o;
    return Objects.equals(name, other.name)
            && Objects.equals(category, other.category)
            && Double.compare(price, other.price) == 0
            && warrantyMonths == other.warrantyMonths
            && stock == other.stock;
}

@Override
public final int hashCode() {
    return Objects.hash(name, category, Double.hashCode(price), warrantyMonths, stock);
}
```

Обидва методи реалізовано один раз у базовому класі й закрито `final`, тому підтип не може порушити узгодженість, підмінивши лише один із них.

### 7.2. Контракт і вибір getClass()

- **рефлексивність:** `x.equals(x)` – перша перевірка `this == o`;
- **симетричність і транзитивність:** порівняння за класом і набором полів однакове в обидва боки; `instanceof` тут небезпечний, бо підтип із додатковою умовою міг би бути «рівним» базовому об’єкту лише в один бік, тому використано `getClass()`;
- **узгодженість:** поля незмінні, повторні виклики дають один результат;
- **`null`:** `x.equals(null)` завжди `false`;
- **зв’язок із `hashCode`:** рівні об’єкти мають однаковий хеш, бо він обчислюється з тих самих полів, що й `equals`; ціна враховується через `Double.hashCode`, узгоджений з `Double.compare`.

Про різні підтипи. Вид товару визначається категорією, а категорія входить до порівнюваних полів, тож два об’єкти з однаковими п’ятьма полями завжди мають один підтип. Перевірка `getClass()` тому не змінює результат для даних, створених через фабрики, але потрібна за контрактом: вона гарантує, що навіть за появи нового підтипу рівність лишиться симетричною. Тест `differentSubtypesAreNeverEqual` створює об’єкти різних підтипів із різними категоріями безпосередньо через конструктори підтипів і перевіряє, що вони нерівні в обидва боки.

### 7.3. Перевірка в колекціях

```text
Set<Product> set = new HashSet<>(List.of(
        Product.of("a", "Ноутбуки", 1, 1, 1),
        Product.of("b", "Монітори", 2, 2, 2),
        Product.of("c", "Смартфони", 3, 3, 3)));

assertFalse(set.add(Product.of("a", "Ноутбуки", 1, 1, 1)));   // дублікат
assertFalse(set.add(Product.fromCsv("b;Монітори;2;2;2")));     // дублікат через fromCsv
assertTrue(set.add(Product.of("a", "Ноутбуки", 1, 1, 2)));      // інший запас

```

## 8. Поліморфізм

Спільний тип використано там, де код працює з товарами як з множиною. Конвеєр `InputProcessor.process` повертає `List<Product>`, `MetricsCalculator` обчислює чотири показники по цьому списку, `WarrantyCostSummary` додає гарантійну вартість. Жоден із цих класів не питає, який підтип має конкретний товар. Різний результат отримується тим, що кожен об’єкт сам знає, як себе порахувати.

```text
public static WarrantyCostSummary of(List<Product> products) {
    Map<ProductKind, List<Product>> byKind = new EnumMap<>(ProductKind.class);
    for (Product product : products) {
        byKind.computeIfAbsent(product.kind(), kind -> new ArrayList<>()).add(product);
    }
    ...
    for (Product member : members) {
        subtotal += member.warrantyCost();      // поліморфний виклик
    }
    ...
}
```

Рядок `member.warrantyCost()` викликає різний код залежно від фактичного класу об’єкта. Групування йде за значенням `enum`, а не за класом (`instanceof` у коді відсутній), і лише готує дані для підсумку.

### 8.1. Чому не центральний if або switch

- **правило живе поруч із типом.** Формула ноутбука знаходиться в `Laptop`, а не в довільному «калькуляторі»; щоб змінити її, не треба шукати всі місця, де порахована вартість;
- **новий підтип не змінює споживачів.** Якщо додати четвертий підтип, `InputProcessor`, `MetricsCalculator` і `WarrantyCostSummary` лишаються без змін, а в центральному `switch` довелося б додавати гілку в кожному місці розрахунку;
- **немає дублювання.** У центральному варіанті ті самі формули повторюються в кожному споживачі; нижче (розділ 12.4) така реалізація порівняна;
- **перевірка тестами залишається простою.** Кожен підтип перевіряється окремо, а споживачі – на змішаному списку.

Доказ у коді: порівняно з `v1.1.0`, файли `InputProcessor.java`, `MetricsCalculator.java`, `CsvReader.java` і `Metrics.java` не змінено взагалі (`git diff v1.1.0 v1.2.0` для них порожній), а конвеєр уже обробляє три підтипи.

### 8.2. Завдання із зірочкою: sealed і вичерпний switch

Клас `Product` оголошено `sealed` з клаузою `permits Laptop, Peripheral, OtherProduct`, а підтипи – `final`. Компілятор тепер знає повний перелік підтипів і може перевіряти `switch` на вичерпність. Це використано в `ProductDescriber.describe`, що словами описує правило розрахунку для звіту:

```text
public static String describe(Product product) {
    return switch (product) {
        case Laptop laptop -> String.format(
                Locale.ROOT, "%s + %.0f грн за кожен розпочатий рік",
                percentPerYear(Laptop.RATE_PER_YEAR), Laptop.SURCHARGE_PER_STARTED_YEAR);
        case Peripheral peripheral -> percentPerYear(Peripheral.RATE_PER_YEAR);
        case OtherProduct other -> percentPerYear(OtherProduct.RATE_PER_YEAR);
    };
}
```

Гілки `default` немає, і це навмисно. Щоб побачити перевірку компілятора, на копії коду (поза репозиторієм) додано четвертий дозволений підтип `Tablet`, а `ProductDescriber` не змінено. Результат `javac`:

```text
src/ua/lpnu/kzp/model/ProductDescriber.java:26: error: the switch expression does not cover all possible input values
        return switch (product) {
               ^
1 error
```

Інший експеримент: клас `Rogue extends Product`, якого немає в `permits`:

```text
src/ua/lpnu/kzp/model/Rogue.java:3: error: class is not allowed to extend sealed class: Product (as it is not listed in its 'permits' clause)
public final class Rogue extends Product {
             ^
1 error
```

Отже, `permits` забороняє появу невідомих підтипів, а вичерпний `switch` без `default` перетворює «забули обробити новий підтип» із прихованої помилки часу виконання на помилку компіляції. Якби в `switch` стояв `default`, компілятор мовчки пропустив би новий підтип, і помилку знайшли б лише тестами або користувачі. Тест `productIsSealedWithTheThreeSubtypes` додатково перевіряє через рефлексію, що `Product` запечатаний і має рівно три дозволені підтипи.

Чому цей `switch` не суперечить принципу «без розгалужень за підтипом». Вимога лабораторної роботи – не дублювати в `switch` логіку, яку вже виконує поліморфний метод. Гарантійна вартість лишається поліморфною (`warrantyCost()`), а `switch` у `ProductDescriber` будує лише текстове пояснення для звіту з тих самих констант (`RATE_PER_YEAR`), тому числа не дублюються й не розходяться. Це свідомий компроміс: пояснення належить до подання, а не до моделі, а вичерпність `switch` змушує оновити текст у єдиному місці при появі підтипу.

### 12.4. Поліморфна реалізація проти центрального розгалуження

Щоб порівняти поліморфну реалізацію з наївною, написано дві альтернативи, які обчислюють ту саму гарантійну вартість поза класами моделі: **B** – центральний `switch` за значенням `kind()` та **C** – центральний `switch` зі зіставленням зі зразком за підтипом. Формули в них ті самі; порівнюється, де вони живуть і що треба змінити при розширенні.

```text
// A: поліморфний виклик
for (Product p : products) {
    total += p.warrantyCost();
}

// B: центральний switch за kind()
for (Product p : products) {
    double years = p.getWarrantyMonths() / 12.0;
    total += switch (p.kind()) {
        case LAPTOP -> round(p.getPrice() * Laptop.RATE_PER_YEAR * years
                + Laptop.SURCHARGE_PER_STARTED_YEAR * Math.ceil(years));
        case PERIPHERAL -> round(p.getPrice() * Peripheral.RATE_PER_YEAR * years);
        case OTHER -> round(p.getPrice() * OtherProduct.RATE_PER_YEAR * years);
    };
}
```

Таблиця 19 – Порівняння за якістю коду

| Критерій | A: поліморфізм | B і C: центральний switch |
|---|---|---|
| розгалужень за підтипом у коді споживача | 0 | 3 гілки в кожному місці розрахунку |
| де записано формулу ноутбука | один раз, у `Laptop` | у кожному споживачі, що рахує вартість |
| що змінити при новому підтипі | новий клас, `permits`, константа `ProductKind`; споживачі не змінюються | кожен `switch` у кожному споживачі |
| що змінити при зміні ставки | одна константа в підтипі | усі копії формули |
| перевірка повноти | компілятор вимагає реалізувати `warrantyCost()` у новому підтипі | B: лише з `switch`-виразом без `default`; C: з `sealed` і `switch` без `default` |
| тестування | кожен підтип окремо, споживач на змішаному списку | кожна гілка в кожному споживачі |

Висновок щодо підтримки: вичерпний `switch` (варіанти B і C) теж змушує оновити код при появі нового підтипу, тож відсутність `default` дає компілятору однакову силу в обох підходах. Різниця – в обсязі: у поліморфному варіанті правило записано один раз і змінюється в одному місці, а в центральному воно розмножується по всіх споживачах, і кожен новий споживач знову повинен реалізувати ті самі гілки.

### 12.5. Порівняння часу виконання

Для додаткових балів виміряно час обчислення сумарної гарантійної вартості 1 000 000 товарів (випадкові категорії, фіксоване початкове значення генератора, 15 прогрівальних і 25 вимірюваних проходів, медіана). Дані й коректність результатів: суми трьох варіантів збігаються (так). Вимірювання виконано на комп’ютері автора: AMD Ryzen 5 4600H (6 ядер, 12 логічних процесорів), 15,4 ГБ ОЗП, Windows 10 Pro (10.0.19045); Java(TM) SE Runtime Environment 21.0.12+7-LTS-205, HotSpot 64-Bit Server VM. Код вимірювання (`WarrantyCostBenchmark.java`) не входить до репозиторію, бо це разовий експеримент.

| Варіант | Запуск 1 | Запуск 2 | Запуск 3 | нс на товар (медіана запусків) |
|---|---|---|---|---|
| A: поліморфний виклик `warrantyCost()` | 15.88 | 16.03 | 15.84 | 15.9 |

У всіх трьох запусках поліморфний виклик виявився повільнішим за обидва центральні `switch`: приблизно 15,9 нс на товар проти 12,1 нс (варіант B) і 11,0 нс (варіант C), тобто в 1,3–1,45 раза; результати запусків відрізняються менш ніж на 0,3 нс, а суми всіх трьох варіантів збігаються до копійки. В абсолютних числах різниця становить 4–5 нс на товар: для мільйона товарів це 4–5 мс, а для реального обсягу магазину (тисячі записів) – мікросекунди, тому на швидкодію програми вона не впливає. Отже, за часом виграє центральний `switch`, за підтримкою коду – поліморфізм (розділ 12.4); у цій програмі, де рахунок вартості не є вузьким місцем, перевага простоти змін важливіша за кілька наносекунд. Вимірювання – мікротест на одному комп’ютері без фіксації плану живлення; на іншому обладнанні числа будуть іншими, але співвідношення потрібно перевіряти заново.

## 14. Відповіді на контрольні питання

**1. Яку спільну проблему розв’язує базовий тип у предметній області?**

Усі товари мають однакові поля, однакові перевірки й спільні операції, а відрізняються лише деякі правила. Базовий тип `Product` збирає спільне в одному місці: п’ять полів, перевірки конструктора, `equals` і `hashCode`, а також оголошення операції `warrantyCost()`. Завдяки йому конвеєр працює зі `List<Product>`, не знаючи конкретного підтипу.

**2. Чим відрізняються extends і implements?**

`extends` означає успадкування від класу: підтип отримує його поля й методи, і в Java клас має лише один базовий клас (`Laptop extends Product`). `implements` означає, що клас виконує контракт інтерфейсу, і таких інтерфейсів може бути кілька. У проєкті використано `extends`, бо підтипам потрібен спільний стан і спільні перевірки, а інтерфейс їх зберігати не може.

**3. Навіщо базовий клас може бути abstract?**

Абстрактний клас неповний: він може мати метод без реалізації й не дозволяє створити власний екземпляр. Товару «взагалі» не існує, є ноутбук, периферія й інше, а правило гарантійної вартості без категорії не визначене. Тому `Product` абстрактний: `new Product(...)` не компілюється, а метод `warrantyCost()` змушує кожен підтип дати власну реалізацію.

**4. Яку роль виконує виклик super(...) у конструкторі підтипу?**

Він викликає конструктор базового класу й має бути першим оператором конструктора підтипу. У `Laptop` рядок `super(ProductKind.LAPTOP, name, category, price, warrantyMonths, stock)` передає базовому класу вид і п’ять полів, а там виконуються всі перевірки й присвоєння. Тому підтип нічого не перевіряє й не дублює.

**5. Що перевіряє анотація @Override?**

Вона просить компілятор перевірити, що метод справді перевизначає метод базового класу (або реалізує метод інтерфейсу) з тією самою сигнатурою. Без неї помилка в імені чи типі параметра створила б новий метод, який ніхто не викликає. З анотацією така помилка стає помилкою компіляції.

**6. Що таке поліморфізм і як він усуває розгалуження за типом?**

Поліморфізм – здатність працювати з об’єктом через базовий тип, а потрібний варіант методу вибирається за фактичним класом під час виконання. Замість `if (p instanceof Laptop) ... else if ...` у коді стоїть один виклик `member.warrantyCost()` у `WarrantyCostSummary`, і кожен підтип сам знає свою формулу.

**7. Коли краще використати інтерфейс, а коли абстрактний клас?**

Інтерфейс доречний, коли різні за природою типи мають спільну здатність і немає спільного стану (наприклад, `Comparable`), або коли потрібно кілька ролей. Абстрактний клас – коли є спільний стан і спільні перевірки, а підтипи є різновидами одного поняття. У мене спільні п’ять полів, перевірки й `final`-`equals`, тому вибрано абстрактний клас.

**8. Що означає відношення «є різновидом» і чим воно відрізняється від композиції?**

«Є різновидом» (is-a) означає, що підтип можна підставити всюди, де очікується базовий: ноутбук є товаром. Композиція (has-a) – коли об’єкт містить інший і делегує йому роботу: `Product` міг би містити `WarrantyPolicy`. Спадкування вибирають, коли відношення справжнє й поведінка не змінюється під час життя об’єкта; композицію – коли поведінку треба міняти або зв’язок не є різновидом. Тут категорія не змінюється, тому вибрано спадкування.

**9. Для чого використовують enum із полями та методами?**

Для фіксованої множини значень, до яких прив’язані дані й поведінка. `ProductKind` має підпис для звіту, множину категорій CSV і посилання на конструктор підтипу. Так уся відповідність категорії, виду й підтипу зібрана в одному місці замість розкиданих «магічних рядків» і ланцюжків `if`.

**10. Чому значення enum можна порівнювати через ==?**

Кожна константа `enum` існує в одному екземплярі на всю програму, тому `==` перевіряє те саме, що й `equals`. Додатково `==` не кидає `NullPointerException` і не дозволить порівняти значення несумісних типів ще під час компіляції. У коді так порівнюється вид: `fromCategory(category) == this`.

**11. Які правила має виконувати пара equals/hashCode?**

`equals` має бути рефлексивним, симетричним, транзитивним і узгодженим, а `x.equals(null)` – завжди `false`. Якщо два об’єкти рівні, їхні `hashCode` мають збігатися; зворотне не обов’язкове. Хеш обчислюється з тих самих полів, що й рівність. У `Product` обидва методи `final` і використовують ті самі п’ять полів.

**12. Чому змінне поле небезпечне для об’єкта, який є ключем HashMap?**

Мапа кладе ключ у кошик за його `hashCode` у момент вставки. Якщо після цього змінити поле, хеш зміниться, пошук піде в інший кошик, і запис «загубиться», хоча залишиться в мапі. Тому всі поля `Product` `private final`, і `hashCode` не змінюється.

**13. Чому два об’єкти різних підтипів можуть бути нерівними за однакової назви?**

Рівність включає клас і категорію: ноутбук і монітор з однаковою назвою – різні товари. Клас у `equals` також потрібен, щоб рівність лишалася симетричною при появі нових підтипів. Тест `differentSubtypesAreNeverEqual` створює `Laptop`, `Peripheral` і `OtherProduct` з однаковою назвою й різними категоріями й перевіряє, що вони попарно нерівні.

**14. Як поліморфна колекція обробляє об’єкти різних підтипів?**

`List<Product>` зберігає посилання на базовий тип, а в ньому можуть бути об’єкти будь-якого підтипу. Цикл викликає `warrantyCost()` для кожного, і кожен об’єкт виконує власний код. Тест `mixedListIsSummedThroughTheBaseType` сумує список із двох ноутбуків, периферії та іншого товару й отримує 2600,00 + 15,00 + 10,00 + 0,00.

**15. Які тести доводять, що підтипи мають різну поведінку?**

`WarrantyCostTest`: для різних підтипів однакового вигляду (ціна, місяці) результат різний – 2600,00 для ноутбука, 15,00 для периферії, 10,00 для іншого товару; лише ноутбук має збір за розпочаті роки (18 місяців дають 650,00), а для 0 місяців усі дають 0. `ProductDescriberTest` перевіряє різні тексти правил.

**16. Які тести доводять коректність рівності в HashSet?**

`hashSetCollapsesDuplicatesOfMixedSubtypes`: додавання дубліката (через `of` і через `fromCsv`) повертає `false`, розмір множини 4, `contains` працює для рівного й не працює для відмінного запасу. `hashMapFindsValuesByEqualKeys`: рівний, але інший об’єкт-ключ знаходить значення. Додатково `equalObjectsHaveEqualStableHashCodes` перевіряє збіг хешів.

**17. Що контролює sealed і навіщо потрібен permits?**

`sealed` обмежує, які класи можуть успадковувати `Product`, а `permits` перелічує їх: `Laptop`, `Peripheral`, `OtherProduct`. Кожен дозволений підтип має бути `final`, `sealed` або `non-sealed`. Спроба додати клас поза переліком – помилка компіляції (експеримент із `Rogue` у розділі 8.2), а компілятор, знаючи повний перелік, перевіряє вичерпність `switch`.

**18. Чому switch за підтипами не повинен дублювати поліморфні методи?**

Інакше правило записане двічі: в підтипі й у `switch`, і при зміні одне з них забувають. Вартість лишається в `warrantyCost()`. `switch` у `ProductDescriber` будує лише текст для звіту з тих самих констант `RATE_PER_YEAR`, тож числа не розходяться, а відсутність `default` змушує оновити текст при появі нового підтипу.

**19. Які попередні тести та результати потрібно зберегти після перебудови?**

Усі 358 тестів лабораторних робіт № 1 і № 2 з тими самими очікуваннями (змінено лише спосіб створення товару), `GoldenReportTest`, звіт для `data/input.csv`: 8 записів, середня ціна 14030.62 грн, гарантія 36, запас 75, 6 пропущених рядків із тими самими повідомленнями, коди завершення, формат CSV. Перевірено порівнянням із `docs/baseline/` і CI на чотирьох виконавцях.

**20. Яке рішення у Вашій ієрархії найкраще демонструє перевагу поліморфізму?**

Підсумок гарантійної вартості в `WarrantyCostSummary`:

```text
for (Product member : members) {
    subtotal += member.warrantyCost();
}
```

Цей цикл не знає про підтипи, тож `InputProcessor`, `MetricsCalculator`, `CsvReader` і `Metrics` не змінювались взагалі (їхній `git diff` між `v1.1.0` і `v1.2.0` порожній), а нові підтипи з різними правилами вже працюють у конвеєрі. Новий підтип потребує нового класу й запису в `permits`, але не торкається коду, що рахує підсумок.

## 15. Висновки

Товар із лабораторної роботи № 2 став базовим типом ієрархії: абстрактний запечатаний `Product` зберігає спільний стан і всі перевірки, `Laptop`, `Peripheral` і `OtherProduct` різняться поліморфним методом `warrantyCost()`, а `enum ProductKind` пов’язує категорію з підтипом і підписом для звіту. Рівність об’єктів узгоджена з хешем і перевірена в `HashSet` та `HashMap`, а `switch` без `default` у `ProductDescriber` показав, що компілятор стежить за вичерпністю ієрархії.

Зовнішню поведінку збережено: звіт без прапорця побайтово збігається з еталоном, що доводять golden-тести й 358 незмінних за очікуваннями старих випадків; конвеєр (`InputProcessor`, `MetricsCalculator`) не змінено. Кількість тестових випадків зросла з 358 до 432 при покритті 98,96 % / 97,44 % і нуль знахідок SpotBugs. CI зелений на Windows, macOS і двох Ubuntu, версія 1.2.0 однакова в `pom.xml`, тезі `v1.2.0` і `--version`, JAR опубліковано в релізі. Порівняння з центральним розгалуженням показало, що поліморфний виклик на мільйоні товарів повільніший на 4–5 нс на товар (у 1,3–1,45 раза), але правило розрахунку записано в одному місці й не вимагає змін у споживачах.

Основою наступної лабораторної роботи є готова поліморфна модель: колекцію `List<Product>` із різними підтипами можна буде обробляти потоками й складеними запитами (групування, фільтрація, агрегування), використовуючи `kind()`, `warrantyCost()`, `equals` і `hashCode`, а звіт і тести, що захищають його поведінку, залишаються незмінною опорою.
